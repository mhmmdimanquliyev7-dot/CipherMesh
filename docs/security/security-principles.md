# Security Principles

Status: Phase 0.5 baseline. These principles are binding for design, code review and the SECURITY REVIEW step in Jira. Each principle states how CipherMesh applies it and how compliance is verified.

| # | Principle | How CipherMesh applies it | How it is verified |
|---|---|---|---|
| 1 | **Least privilege** | Four room roles with minimal permissions (ADMINs cannot create ADMINs); PLATFORM_ADMIN has no room access; separate database roles for migrations, API and worker; object-storage credentials scoped to one bucket; WebCrypto key usages restricted to what each key needs; non-root containers | Authorization matrix tests; database grant review; container configuration review; key-usage unit tests |
| 2 | **Defense in depth** | Authorization and encryption protect content independently; Nginx and the API both limit requests; CSP plus React escaping plus text-only rendering against XSS; SameSite plus same-origin verification plus a custom request header against CSRF; server-enforced write lock plus client version checks for rekeys; append-only grants plus hash chain plus anchored checkpoints for audit; provider encryption at rest under client-side encryption | Threat model lists at least two controls for each high risk; tests for each layer |
| 3 | **Secure by default** | New rooms default to CONFIDENTIAL in the UI; burn-after-reading is on by default; cookies are HttpOnly, Secure and SameSite=Strict; buckets are private; the API container publishes no host port | Configuration tests; deployment checklist evidence |
| 4 | **Deny by default** | Every route requires authentication unless allowlisted; unknown actions are denied by `authorize()`; the firewall denies all inbound traffic except 22 (allowlisted sources), 80 and 443; unknown request fields are rejected | Route inventory test; firewall scan evidence; schema tests |
| 5 | **Explicit authorization** | Every route declares its action ID; one central decision function; object-level rules OL-01 to OL-12 | Startup check for undeclared routes; BOLA suite |
| 6 | **Cryptographic key separation** | Different keys for each purpose (PKWK, RWK_v, DEKs, server keys); HKDF with distinct canonical contexts; auth password separate from the Vault Passphrase; RKM_v never used directly; server keys never touch content | Key-hierarchy review; tests that contexts differ per purpose and that cross-context decryption fails |
| 7 | **No secret material in logs** | Central logger with a redaction list; handlers never log bodies of auth, vault, key, note or secret endpoints; audit details use per-action allowlists; presigned URLs never logged | Log-redaction regression tests; a canary test that sends known secrets through every endpoint and searches the logs for them |
| 8 | **No plaintext sensitive room content in persistent server storage** | Files, filenames, note content and secrets are encrypted in the browser; plaintext hashes only inside encrypted manifests | Canary scans of the database and object storage after E2E runs; schema review against the "must never exist" list |
| 9 | **No homemade cryptography** | WebCrypto, Node.js `crypto` and registered libraries only; compositions specified in `docs/crypto`; parameters only from the register | Code review rule; dependency review; known-answer tests against published vectors |
| 10 | **Fail securely** | Tag or commitment failures show no plaintext; missing Argon2id fails closed; invalid configuration stops the API at startup; errors return generic messages; a room that lost a member stays write-locked until the rekey completes | Tamper tests; startup configuration tests; error-response tests |
| 11 | **Validate at trust boundaries** | Schemas for every request and response; configuration validated at startup; client verifies commitments, fingerprints and response schemas; storage uploads verified at completion | Schema tests; fuzzing of API inputs during assessment |
| 12 | **Minimize exposed services** | Only Nginx is reachable from the internet; static frontend without a Node.js server; database and storage reachable only from the VM or through presigned URLs; no admin panels exposed | External port scan; cloud firewall and security-group evidence |
| 13 | **Security controls must be testable** | Every control in the policy profiles and authorization matrix has an automated test; evidence plan defines what to capture | CI security suite; evidence index |
| 14 | **Security-sensitive decisions are documented** | ADRs for architecture and cryptography; crypto decision log; threat model updated with changes | Pull-request checklist; SECURITY REVIEW gate in Jira |
| 15 | **Never silently weaken security to ease implementation** | Any weakening needs an ADR, an updated threat model and explicit approval by the project owner; no disabling of tests or authorization | Review checklist; CLAUDE.md rules for every session |

## Honest-claims rule

A principle that cannot be fully met is documented as a limitation, not hidden. Marketing-style claims ("unhackable", "military grade", "zero knowledge", "tamper-proof") are forbidden in code, UI text, documentation and the report. See [limitations.md](limitations.md).
