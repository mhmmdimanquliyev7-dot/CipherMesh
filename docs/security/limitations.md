# Security Limitations

Status: Phase 0.5 baseline; L-26 to L-29 added in Phase 2; L-30 to L-36 added in Phase 3; L-37 to L-41 added and L-08, L-09, L-17, L-23, L-33 and L-36 updated in Phase 4. L-42 to L-45 added and L-33 updated in Phase 5. L-46 added and L-09, L-23, L-43 and L-44 updated in Phase 6. L-47 to L-50 added in Phase 7, L-51 to L-54 in Phase 8 and L-55 to L-58 in Phase 9. These limitations are part of the security model, not defects to hide. Demonstrating them is academically valuable, so several have a suggested demonstration for the final report. IDs (L-xx) are referenced throughout the documentation.

| ID | Limitation | Why it exists | What CipherMesh does | Demonstration idea |
|---|---|---|---|---|
| L-01 | **A compromised browser or device can read plaintext** while the legitimate user has it decrypted, and can capture the Vault Passphrase as it is typed | Decryption must happen somewhere the user can read the result | Keys only in memory, non-extractable where possible, vault auto-lock, no persistence of plaintext, guidance for RESTRICTED rooms | Show that a script with page access can read decrypted note text but cannot export the non-extractable private key |
| L-02 | **Client-side encryption does not protect against a malicious web application served after server compromise.** Whoever controls the served JavaScript can capture passphrases and plaintext | Browsers fetch application code from the server on each visit; there is no general mechanism for users to pin code of ordinary websites | Static, content-hashed assets built in CI from reviewed commits; strict CSP; no third-party scripts; published build hashes; hardened VM | Explain in the report with the trust-boundary diagram (TB-03); compare with native apps and browser extensions such as code-verification extensions |
| L-03 | **Burn-after-reading cannot stop the recipient from copying the plaintext** (copy and paste, screenshots, photos) | Anything a person can read, they can record | Clear UI warning; secrets rendered as text; at-most-once delivery | Reveal a secret, copy it, show that the server copy is gone but the copied text remains |
| L-04 | **Key rotation protects future data only.** It cannot revoke plaintext or keys that a removed member already obtained | Knowledge cannot be taken back | Mandatory rotation on removal, immediate loss of API access, audit trail | Remove a member, show that new content uses version v+1 and that the old key cannot unwrap new DEKs, while old downloads stay readable offline |
| L-05 | **Metadata is visible to the server**: room names, membership, roles, sizes, timestamps, access patterns, IP addresses in sessions | The server needs metadata to authorize, enforce policy and audit | Filenames, types and note titles encrypted; room names flagged as non-confidential; retention limits for IP data | Show a database row: ciphertext for content, clear text for room name and sizes |
| L-06 | **Availability depends on the cloud provider and one VM** | Single-region, single-VM design chosen for simplicity | Managed database backups, object versioning, documented restore procedure | Restore test evidence |
| L-07 | **The server is the public-key directory.** An attacker controlling the server or database could substitute public keys unless users compare fingerprints out of band | No independent key directory or transparency log | Fingerprints in the UI, mandatory confirmation in RESTRICTED rooms, audited key changes, keys bound to envelope labels. The Room Safety Code does not detect substitution | Simulate a substituted key in a test database and show the fingerprint mismatch in the RESTRICTED invitation flow |
| L-08 | **Weak Vault Passphrases can be guessed offline** by anyone holding a copy of the database | The encrypted private key must be stored somewhere accessible to all devices of the user | Argon2id with memory-hard parameters (Phase 4: m = 64 MiB, t = 3, p = 1, CP-04), a minimum of 16 characters, a 3,350-entry blocklist and identity checks, a new salt on every vault write, no server-side verifier | Show the time for one Argon2id derivation (`pnpm bench:vault`) and extrapolate guessing cost for short versus long passphrases |
| L-09 | **Attribution among members relies on the server.** A shared room key proves "someone with the room key" produced a ciphertext, not which member | Content items are not signed. Per-user signing keys (CD-23, ADR-015) attribute room key versions and membership grants since Phase 6, not individual files, notes or secrets | Uploader recorded from the authenticated session; audit trail; signed key versions, genesis statements and grants (Phase 6) | Explain with the key hierarchy |
| L-10 | **The server can withhold data or serve an older version** of mutable data such as a note or the vault record | Clients have no independent record of the latest state | Revision numbers in AAD, optimistic concurrency, audit events | Explain; optional test that swapping revisions fails authentication |
| L-11 | **Encrypted files cannot be scanned for malware** by the server | The server never sees plaintext | Files never rendered or executed by the server; downloads forced as attachments; warnings; size limits | Upload a harmless test file (for example the EICAR test string) and show it is stored only as ciphertext |
| L-12 | **Backups retain deleted, expired and burned ciphertext** until backup retention ends | Managed backups and object versioning are outside per-item control | The data stays encrypted; retention periods documented | Show backup retention settings |
| L-13 | **The audit ledger is tamper-evident, not tamper-proof.** An attacker with full database access can rewrite events after the last anchored checkpoint, and a compromised server can simply stop recording events | Hashes detect changes only against a trusted reference | Append-only grants, hash chain, signed checkpoints in retention-locked storage, external witness copies, offline verifier. Trust model per compromise scenario in ADR-009 section 8 | Modify an event in a test database and show the verifier pinpointing it |
| L-14 | **Download and "view-only" restrictions cannot be enforced cryptographically** | Whoever can decrypt can save the plaintext | PC-12 controls whether the API issues ciphertext at all | Explain in the policy section |
| L-15 | **JavaScript cannot reliably wipe memory** | Garbage collection, immutable strings, JIT copies | Minimize key lifetime, non-extractable keys, auto-lock | Explain |
| L-16 | **No post-quantum protection.** RSA-OAEP envelopes recorded today could be decrypted by a future large quantum computer | Standard post-quantum KEMs are not yet available in WebCrypto | Algorithm suite identifiers allow future migration | Explain |
| L-17 | **Losing the Vault Passphrase loses the personal key**; access returns only if admins re-share room keys, and only for versions the history policy allows | No key escrow by design | Vault reset to a new identity (Phase 4), re-share flow (Phase 6 onward); the optional user-held recovery key (OCD-10) is not implemented | Demonstrate a vault reset and, from Phase 6, a re-share |
| L-18 | **Fingerprint confirmation cannot prove that people compared fingerprints** | The server only sees the confirmed value | Mandatory confirmation step in RESTRICTED rooms, clear UI instructions | Explain |
| L-19 | **Audit records only server-observable actions.** Client-side decryption is not observable | Decryption happens in the browser | Audit records ciphertext issuance (for example download URLs), not "file opened" | Explain in the audit section |
| L-20 | **No resistance to large-scale DDoS** | No CDN or WAF in the baseline | Nginx and API rate limits, body-size limits | Explain |
| L-21 | **Account identifiers (email addresses) are not verified**, so a look-alike account can be invited by mistake | No email service in the baseline | Identifiers labelled unverified; fingerprints and account age shown at invitation; confirmation required in RESTRICTED rooms (T-35) | Register a look-alike test account and show the fingerprint mismatch in the invitation dialog |
| L-22 | **The Room Safety Code detects key inconsistency only when members actually compare it over an independent channel.** It does not show who else holds the key, does not detect a key that every member received from an attacker (T-36) or key substitution with re-wrapping (T-25), and malicious JavaScript can display a fake code (L-02) | The code is derived from the key each browser holds, so it can only show whether two members hold the same key | Optional comparison with advisory prompts, clear wording, mismatch reporting (ADR-012) | Give two test browsers different keys through a test harness and show that their codes differ |
| L-23 | **Room-key versions are authenticated by signatures from Phase 6, which leaves identity substitution, a legitimate member's keys and the served code as the ways to inject a key (T-36).** A server-side attacker without a member's signing key can no longer give members a key of its own: clients refuse an unsigned, wrongly signed or unauthorized version (ADR-015 section 4.1) | RSA-OAEP has no sender authentication and public keys are public, so authenticity comes from ECDSA signatures over the commitment and the recipient list, checked against a chain of signed grants back to the signed genesis statement | Implemented in Phase 6 (CM-T033, CM-T036): the `key-injection` suite, the API's own signature checks and NC-06-01 to NC-06-05. Not covered: a substituted identity under a user ID (T-25, L-07), an authorized OWNER or ADMIN colluding with the server (L-22), rekeyed versions (Phase 11), and grants as statements rather than revocable credentials (L-46) | `packages/crypto/src/room-keys.test.ts` (injected, forged and unauthorized versions are refused) |
| L-24 | **A mandatory rekey needs an OWNER or ADMIN with an unlocked vault.** Until one completes it, the room is read-only | Only member browsers hold room keys; the server cannot rotate them (ADR-013) | Immediate prompt to the removing admin, banners, a count on the Security Dashboard, lease-based recovery from crashes | Show a write-locked room and its recovery after a simulated crash |
| L-25 | **At Level 1 the audit signing key is stored on the application VM.** A VM compromise also compromises checkpoint signatures from then on | No independent key custody in the baseline | Worker-only key file, retention-locked anchors, weekly external witness copies, optional Level 2 provider key (OCD-13) | Explain with the audit trust model; revoke a test key and show the verifier rejecting later signatures |
| L-26 | **The database owner can switch off the append-only protection.** The migration role (table owner) or a superuser can disable the audit trigger, alter the table or drop it | PostgreSQL gives table owners full control; the migrations need an owner | Runtime roles hold only SELECT and INSERT; triggers reject UPDATE, DELETE and TRUNCATE for every role; the migration credential never lives on the VM. Detection comes from the hash chain and external checkpoints in Phase 12 (ADR-009); until then, a modification by the owner is not detectable | `tests/database/audit.test.ts` disables the trigger as the owner inside a rolled-back transaction |
| L-27 | **Database constraints check shapes, not meaning.** A CHECK can require 384 bytes in an envelope column, but cannot tell an RSA-OAEP ciphertext from 384 bytes of plaintext. The forbidden-field checker reads names, not values | The server cannot decrypt, so it cannot verify ciphertext semantics | Sizes and NULL rules in CHECK constraints, client-side encryption in packages/crypto, response projections, and the planned canary scan of database dumps (T-01) | Insert 384 bytes of readable text as an envelope in a test database: the constraint accepts it, the canary scan finds it |
| L-28 | **Local database roles differ from the managed service.** Locally the container administrator is a superuser; the managed provider's administrator is not, and provider IAM decides who reaches the instance | Development runs on a single container | The same role names, attributes and grant migration in both environments; the provisioning of the managed database (CM-T067, Phase 18) records the cloud side | Compare `tests/database/privileges.test.ts` output locally and against the managed database in Phase 18 |
| L-29 | **The local development database has no TLS.** It listens on 127.0.0.1 only | TLS on the developer container adds certificate management without protecting a loopback connection | Outside production, the API accepts a connection without `sslmode=verify-full` only to a loopback host; production requires `verify-full` | `tests/security/startup-config.test.ts` |
| L-30 | **Anyone who knows an email address can delay that user's login.** Wrong passwords for the address trigger the progressive backoff (up to 15 minutes at a time) | There is no permanent lockout on purpose; a backoff that an attacker cannot trigger would also not stop the attacker | Backoff capped at 15 minutes, never permanent; per-address limits slow the attacker; MFA does not depend on the backoff; events show the pattern | `tests/auth/abuse.test.ts`: five wrong passwords block the right one for 30 seconds |
| L-31 | **The TOTP encryption key cannot be rotated yet.** Only one key is active; a rotation needs a re-encryption tool | Built in Phase 3 without key-rotation tooling | The key ID is stored with every ciphertext, so rotation can be added without a schema change; the key lives outside the database | Explain; planned with the deployment secrets work (Phase 17) |
| L-32 | **Rate limits are per process and in memory.** A restart resets them, and several API instances would each count separately | The baseline runs one API process on one VM | Per-account backoff is stored in the database and survives restarts; Nginx limits are added in Phase 17 | Restart the API and show that the account backoff persists while the address window resets |
| L-33 | **Authentication, vault and room authorization security events are written to the application log, not yet to the tamper-evident audit ledger.** A VM-level attacker can alter or delete log lines | INV-09 requires hash-chained audit rows; the chain is built in Phase 12, and append-only rows inserted earlier could never be chained | One event catalogue and one sink, so Phase 12 switches all call sites at once; login attempts are also kept in the database | Explain with the audit trust model |
| L-34 | **TOTP can be phished in real time.** A fake site can relay a code within its validity window | TOTP has no origin binding; WebAuthn is a stretch goal (OCD-11) | Short validity, replay protection, step-up for sensitive actions, CSP and no third-party scripts | Explain; compare with passkeys |
| L-35 | **Registration reveals whether an email address is already registered** (409) | Silent acceptance needs an email service for verification, which the baseline does not have (DF-01, T-15) | Rate-limited per address; login itself reveals nothing | `tests/auth/registration.test.ts` |
| L-36 | **The breached-password lists are a static snapshot.** New breaches are not reflected until the list is rebuilt | Online breach checks would send password material (even hashed prefixes) to a third party | 30,402 entries for account passwords and 3,350 for Vault Passphrases from the UK NCSC and Pwdb lists, rebuilt reproducibly by a pinned, checksum-verified script; length matters more than the list | Show a refused common password and the rebuild script |
| L-37 | **The Vault KDF parameters were chosen from laptop measurements only.** No phone was measured, and on slow phones a derivation may take several seconds | No mid-range phone was available in Phase 4, and Chromium's CPU throttling does not slow the worker proportionally, so it is no substitute | The target was not raised beyond m = 64 MiB, t = 3, keeping a margin; parameters are stored per vault and can be raised later by a signed re-wrap; a 120-second timeout fails clearly instead of hanging | Run `pnpm bench:vault` on a phone browser when one is available and record it in crypto-decisions section 8 |
| L-38 | **The vault lock is client-side behaviour.** The server cannot verify that a browser locked its vault, and modified or malicious client code can keep keys in memory | Only the browser holds the unlocked keys; the server never sees them | Auto-lock after 15 minutes without trusted user input, on sign-out, on `pagehide`, when the session ends and after a reset; keys are non-extractable; tested in three engines | Leave a test vault idle and show it locked; explain why the server cannot enforce it |
| L-39 | **Anyone holding a valid session can download the owner's encrypted vault record** and guess the passphrase offline, as a database thief could (L-08) | Every device of the user must be able to fetch the record before it can be unlocked; requiring a step-up for each unlock would not add secrecy, because the record is designed to be safe to store | Session controls (T-08), vault read limits per user, Argon2id cost and the passphrase policy; the record never contains a verifier | Explain with T-22: the session gives the same material as a database copy, for one user |
| L-40 | **A passphrase change does not replace the keys.** Someone who has an old copy of the vault record (for example from a backup or an earlier download) and learns the old passphrase can still open the same private keys | Re-wrapping keeps the identity, so contacts do not have to verify a new fingerprint | Recommend a vault reset (new identity) after a suspected passphrase leak; the UI says so on the passphrase-change form | Change a test passphrase, then open a saved copy of the old record with the old passphrase |
| L-41 | **The directory reveals whether an email address has a cryptographic identity.** A signed-in user with a vault can test addresses | Inviting someone requires finding their public key by address (CM-T027) | Exact match only, an own vault required, the same 404 for unknown, vault-less and disabled accounts, 20 lookups per 10 minutes per user, throttling events; registration already reveals taken addresses (L-35) | `tests/vault/reset-and-directory.test.ts` |
| L-42 | **Profile access rules are checked when a room is created, not yet on every room request.** PC-01 (an MFA-verified session) and PC-02 (a recent password sign-in) bind the creator; members reach a CONFIDENTIAL or RESTRICTED room without them, and RESTRICTED removals need no step-up (PC-03), until the policy gates exist | The roadmap builds the policy engine (CM-T046, CM-T047) in Phase 10, after rooms (Phase 5) | Room creation applies PC-01 and PC-02 from constants compared with the profile table; in Phase 5 a room has only the members an OWNER or ADMIN placed there, since invitations arrive in Phase 6 | `tests/authz/rooms-lifecycle.test.ts` (creation); the access gap is shown by entering a CONFIDENTIAL room with a session without MFA |
| L-43 | **Rooms created before Phase 6 have no key version and stay without one.** They record key version 1 but hold no genesis statement, key version row or envelope. New rooms cannot be created without key version 1 (CM-T033) | Room keys are created in the browser, and the server must never create or backfill one (INV-04). No document describes a client-side initialization of an existing keyless room, and none was invented | Such a room cannot be invited to (no envelope set can name a version it lacks), holds no content, and its key panel says there is no key. The only rooms of this kind are development and test rooms of Phases 5 and 6: nothing is deployed. A transition, if ever needed, requires an architecture decision before it is built | Database view of a legacy room: no `room_key_versions` or `key_envelopes` rows; `tests/authz/room-keys.test.ts` (a room without a genesis statement has no keys to open) |
| L-44 | **A room that loses a member before Phase 11 stays REKEY_REQUIRED until the rekey state machine exists, and a re-enabled account or a reset identity does not get its rooms back.** Removal and account suspension lock the room for content writes and invitations (PC-16); nothing can unlock it before CM-T050 and CM-T051, and a suspended member is reinstated, or a reset identity receives keys again, only through the re-share flow (AZ-14), which the backlog assigns to CM-T053 in Phase 11 and Phase 6 does not implement | INV-07 requires the lock in the same transaction as the loss; faking a rekey would break it. Re-sharing is only safe together with the rekey rules of ADR-013 | The lock is real and visible in the UI; reads and membership administration continue; invitations and acceptances are refused with 409 `REKEY_REQUIRED` while the room is locked (Phase 6); until content writes exist (Phase 7) the lock blocks nothing else | Remove a member, then show the room's key state, the refused invitation and the notice in the UI |
| L-45 | **Room creation reveals whether a known room ID was ever used, and has no per-user quota.** A creator who submits the ID of an existing or deleted room gets 409 `ROOM_ID_UNAVAILABLE`; any account with a vault can create many rooms | Room IDs are chosen by the browser because they enter cryptographic contexts (DF-05); deleted rooms keep a tombstone | UUIDv4 IDs cannot be guessed (OL-09), so only someone who already knows an ID learns that it was used, never whether the room still exists; creation needs an ACTIVE vault; rate limits for the API arrive with Nginx (Phase 17) | `tests/authz/rooms-lifecycle.test.ts` (reused ID) |
| L-46 | **A signed membership grant is a statement, not a revocable credential.** The verification rule of ADR-015 section 4.1 cannot see a demotion, a removal or an ownership transfer away: an earlier grant still counts as authority there, and the key-version signer must only have held OWNER or ADMIN authority at some point | Grants are signed once and stored; the rule is evaluated by each client from signed statements alone, and a signed removal or demotion statement is not part of the Phase 6 design | Membership and roles are enforced by the API (INV-05, INV-07). Members cannot be added to a version's readers by an old grant alone, because they also need an envelope, which only a holder of the key can create. The point matters from Phase 11, when members other than the creator sign key versions: CM-T050 must decide how a former ADMIN's signature is rejected (for example by a signed demotion statement or by the membership epoch) | Remove an ADMIN, then show that a version signed by that ADMIN before the removal still verifies in the browser; planned with the Phase 11 tests |
| L-47 | **File size, upload time and file count are visible to the server and to the storage provider; files are limited to 50 MiB and have no resumable upload.** Ciphertext length is plaintext length plus 16 bytes (T-28). A file is encrypted in one operation in browser memory and uploaded in one request; an interrupted upload starts over. **Browser memory use at the 50 MiB limit was not measured:** no tested engine reported page memory, so the figure rests on an estimate of a few hundred MiB for the plaintext, ciphertext and transient WebCrypto copies (crypto-decisions section 9), and phones were not tested. Chunked or streaming encryption (OCD-09) would need its own ADR | CP-19 single-shot design | The limit is enforced by the browser, the schema, a database CHECK and the signed content length; the UI states it; the benchmark of CP-19 shows 50 MiB encrypted and decrypted in about 150 ms to 0.9 s on a laptop; measure memory and test phones before raising the limit | `pnpm bench:files`, `tests/files/files-upload.test.ts` |
| L-48 | **Removing a member does not take back files they already downloaded or ciphertext they already fetched.** After removal the API refuses their requests, and the next key version protects new files once the rekey exists (Phase 11); a file stored under an older key version stays readable to anyone who holds that version. A downloaded file is saved unencrypted on the member's device, outside CipherMesh | Authorized members can decrypt; "view-only" cannot be enforced (L-14) | The UI says so next to the file list; removal sets REKEY_REQUIRED so no new file is written under the old key; no re-encryption of history (CD-12) | `tests/files/files-upload.test.ts` (write lock), the Files panel text |
| L-49 | **Deleted and expired files can survive in backups, object versioning and downloaded copies** (see L-12). In the live system the row is a tombstone without the wrapped FEK or manifest, and the object is deleted at once or by the worker with retries | Provider backups and versioning are outside per-item control | Reads refuse expired files before the worker runs (INV-14); lifecycle rules on the bucket are a safety net (Phase 19) | `tests/files/files-access.test.ts`, `files-cleanup.test.ts` |
| L-51 | **Note metadata is visible to the server**: who wrote and who last changed each note, how often it changes (the revision), when, its expiry, and its approximate size (ciphertext length is the document length plus 16 bytes). Titles are encrypted with the body, so the server cannot tell titles from bodies | The server needs identifiers and revisions to authorize, order saves and expire notes | No padding; the room's note count is bounded (D-08-01) | `tests/notes/notes-lifecycle.test.ts` |
| L-52 | **Notes keep only the current revision and have no merge.** Two editors who start from the same revision cannot both save: the second gets a conflict and must merge by hand from the text kept in the editor. A deleted or overwritten revision cannot be restored from the live system | Version history and collaborative editing are not in the Phase 8 scope (DF-12: only the current revision is stored) | Optimistic concurrency with 409 and no lost text in the editor; deletion asks for confirmation | `tests/notes/notes-lifecycle.test.ts`, `tests/e2e/notes.spec.ts` |
| L-53 | **Who wrote or changed a note is the server's statement, not a signature** (see L-09). Any member with the room key can produce a valid note ciphertext; `authorId` and `updatedById` come from the session that stored it | Content items are not signed (CD-23 scope) | Server-side authorization of every write; events record the actor | `tests/notes/notes-access.test.ts` |
| L-54 | **Removing a member does not take back notes they already read or copied**, and until the rekey exists (Phase 11) notes stay encrypted under key versions the removed member held. After removal the API refuses every note request from them, and the room refuses new note content until a key rotation (INV-07) | Plaintext a member saw is outside CipherMesh; the rekey is Phase 11 | API refusal (404) at once; REKEY_REQUIRED blocks new content | `tests/notes/notes-access.test.ts` |
| L-50 | **The file name, type and size shown for a file come from the uploader's browser.** A member who uploads can choose any name or MIME type; the manifest is authenticated, not truthful. The browser sanitizes names before saving, never renders HTML or SVG, previews only raster images through a `blob:` URL, and warns before saving executable types, but cannot judge file contents | The server cannot scan or parse ciphertext (L-11) | Text-only rendering; forced attachment downloads; allowlisted previews | `tests/e2e/files.spec.ts`, `packages/crypto/src/files.test.ts` |
| L-55 | **Secret metadata is visible to the server and to the room's OWNER and ADMINs**: who sent a secret to whom and for which identity key, whether it burns after reading, its lifetime, when it was created, revealed, revoked or expired, and its approximate size (ciphertext length is the document length plus 16 bytes). The reveal time tells the sender and the administrators when the recipient opened it | The server needs these facts to authorize, release once and expire secrets; OWNER and ADMIN need the list to revoke (AZ-25, OL-14) | Text and SEK never leave the sender's and the recipient's browsers; MEMBERs and VIEWERs see only what they sent or received; lists never carry ciphertext | `tests/secrets/secrets-lifecycle.test.ts` (lists) |
| L-56 | **Who sent a secret is the server's statement, not a signature** (see L-09, L-53). Anyone holding the recipient's public key, including a compromised server, can produce a valid secret for them; the sender shown comes from the session that stored it | Secrets are not signed: DF-09 and CD-06 specify envelope encryption only, and signing content would need an ADR (CD-23 scope) | Server-side authorization of every creation; the recipient key is authenticated against the room's signed statements, so a secret is readable only by the intended member; creation events record the actor | Explain in the report: authenticity of the content (AES-GCM) is not authenticity of the sender |
| L-57 | **Burn-after-reading is at most once, not exactly once, and proves release, not reading.** The server destroys the ciphertext in the transaction that returns it: if the response is lost, the tab closes or decryption fails after that commit, the secret is gone. The server can show that it released the ciphertext once; it cannot show that the browser decrypted it or that a person read or understood it. A server or database operator who copies the row before the reveal keeps ciphertext that only the recipient's key opens (see L-12), and a malicious server can withhold or delete secrets | This is the trade-off DF-09 chose: a retry that could deliver twice would break one-time retrieval | POST-only reveal after an explicit, warned click; the vault must be unlocked before the request is sent; a non-burn option exists outside RESTRICTED rooms; the UI states the trade-off | `tests/secrets/secrets-concurrency.test.ts` (client disconnect) |
| L-58 | **Revealed text in the browser is dropped, not wiped.** Hiding a secret, locking the vault or leaving the page removes it from the page and from React state, but JavaScript cannot erase strings from memory; the garbage collector reclaims them later. The recipient's screen, clipboard, screenshots and memory dumps are outside CipherMesh (L-01, L-03) | The web platform has no secure-erase primitive for strings | Text kept only in component state, never in browser storage, URLs, titles or notifications (E2E storage checks); raw SEK bytes are overwritten inside the crypto package | `tests/e2e/secrets.spec.ts` |

## Wording rules for the report and UI

- Say "client-side encrypted", "authenticated encryption", "tamper-evident", "the server cannot decrypt stored room content".
- Do not say "unhackable", "military grade", "zero knowledge", "perfectly secure", "tamper-proof", or that removed members "lose access to everything".
- Do not say that the commitment or the Room Safety Code protects against a malicious server. Say that comparing Safety Codes can reveal that members hold different keys.
- When describing a control, name its limitation nearby, with a link to this document.
