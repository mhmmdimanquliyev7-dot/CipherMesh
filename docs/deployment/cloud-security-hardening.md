## 2. Design decisions and trade-offs

### 2.1 Why the storage gateway is public

Browsers upload and download ciphertext directly with presigned URLs, and those URLs must be on another host than the application (SF-07-01). Nginx therefore publishes the S3 object paths of one bucket on the storage host name, and nothing else: no listing, no other bucket, no SeaweedFS master, volume, filer or IAM endpoint, and no request without a signature. SeaweedFS verifies each signature; the URLs expire after 5 minutes (upload) or 60 seconds (download, CP-20).

### 2.2 Egress

The VM needs outbound HTTPS for package updates (Ubuntu), images (Docker Hub), the source (GitHub), dependencies during image builds (npm registry), certificates (Let's Encrypt) and nothing else. The API, worker, database and storage containers sit on internal networks and have no egress at all; Nginx's edge network has egress only for answering clients. The security list allows all egress because OCI security lists cannot filter by host name; the containers' isolation is the effective control.

### 2.3 SSH source restriction

The security list allows SSH only from the operator's address. The host firewall allows SSH from any source (`cm-firewall apply any`) because the operator's home address can change: a stale address in both layers would lock the operator out until the serial console is used. Password and keyboard-interactive authentication and root login are off, so the host layer still allows only key-based logins of one user.

## 4. Findings

Findings of the cloud workstream are recorded here with the Security Finding template's fields and in Jira.

| ID | Severity | Finding | Status |
|---|---|---|---|
| SF-17-01 | Low | The first rehearsal on Linux showed the rehearsal's TLS keys created with mode 0600 for the runner user, so Nginx (uid 101) could not start; on the VM `cm-tls install` gives the keys to uid 101. Fixed in `cm-rehearsal` (rehearsal files only). | Fixed (2026-10-14) |
| SF-17-02 | Low | `cm_psql_superuser` dropped psql options after the database name, so backup manifests would have contained formatted tables instead of digests and a drill comparison would have been meaningless. Found in review before any backup existed; fixed, and the CI stack check now compares manifests. | Fixed (2026-10-14) |
| SF-17-03 | Low | The local Docker demonstration showed the general API limit in Nginx (20 requests per second, burst 40, per address) refusing legitimate page loads when two sessions share one address (two browser windows on one laptop, or users behind one NAT): the room page answered "Unexpected response from the server". The general limit was raised to 50 per second with a burst of 100; the authentication limits (10 per minute) and the API's own per-account limits are unchanged, and the deployment tests pace their sign-ins instead of raising them. | Fixed (2026-10-14) |
| SF-17-04 | Low | The local WebKit run (Playwright WebKit on Windows) lost its session right after a step-up: the browser sent the next request with the token the step-up had just replaced, the API refused it (correct) and answered with a cookie deletion, which the browser applied to the new session cookie. The same race exists in any browser for a request in flight during a rotation. The 401 for a refused token no longer deletes the cookie; the token is still refused, and logout and revocation of the current session still delete it. Regression test in `tests/auth/step-up.test.ts`. | Fixed (2026-10-15) |
| SF-17-05 | Low | The restore drill reported every file object as an error (CI run 38606755583 on linux/arm64, then locally): its check started while the freshly restored SeaweedFS answered its S3 port but did not serve objects yet. A first fix (waiting for an HTTP answer) could never succeed, because `wget` exits non-zero on the expected 403 and `pipefail` hid the match. The wait now reads the answer before matching, and the object check retries a failed fetch for up to a minute and reports the retries and their status codes; a missing object, a size or digest mismatch or a persistent failure still fails the drill. | Fixed (2026-10-15) |
