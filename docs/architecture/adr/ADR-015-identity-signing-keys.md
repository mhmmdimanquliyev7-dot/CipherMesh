# ADR-015: Per-user signing keys and signed room-key versions (OCD-12)

- Status: **Accepted** (2026-10-05, by the project owner before the Phase 4 implementation began). Decides OCD-12 (Jira CM-T086). Sections 1 to 3 are implemented and tested in Phase 4; section 4 is accepted in principle and is confirmed or revised by the Phase 6 and Phase 11 tests
- Date: 2026-10-05
- Related: [ADR-004](ADR-004-key-management.md), [ADR-007](ADR-007-asymmetric-key-wrapping.md), [ADR-012](ADR-012-room-safety-code.md), [ADR-013](ADR-013-rekey-state-machine.md); [crypto-decisions.md](../../crypto/crypto-decisions.md) CP-15 to CP-18, CP-26, CD-11, CD-23, CD-24; [cryptographic-architecture.md](../../crypto/cryptographic-architecture.md) sections 5, 7.5 and 7.6; T-25, T-29, T-32, T-36; L-07, L-09, L-23; AG-01, AG-03 in [architecture-gate-phase-0-5.md](../../security/architecture-gate-phase-0-5.md); CM-T025 to CM-T028, CM-T033 to CM-T036, CM-T050, CM-T053

## Context

Room key material RKM_v reaches members as RSA-OAEP envelopes (ADR-007). RSA-OAEP has no sender authentication, public keys are public, and the key commitment RKC_v is served by the same server that serves the envelopes. A server-side attacker can therefore generate key material of its own, wrap it to every member, store a matching commitment and mark the version current. Every member accepts it, and every Room Safety Code matches because everyone holds the same attacker-known key (T-36, AG-01, L-23). The commitment and the Safety Code detect inconsistency between members (ADR-012); neither can detect a key that all members received consistently.

The decision has to be taken before Phase 4, because every candidate fix changes what a user's cryptographic identity contains, and Phase 4 creates the first identities and the vault format that stores them.

## Threat being addressed

| In scope | Out of scope (unchanged, documented elsewhere) |
|---|---|
| An attacker who can write the database or forge API responses but does not control the JavaScript delivered to browsers: SQL injection through the API role, stolen `cm_api` credentials, a tampered backup or managed-database exposure (ADV-6), and an API-process compromise that cannot replace the static assets | An attacker who controls the code served to browsers, for example root on the VM (ADV-7). Such code performs the verification itself and can skip it (T-24, L-02) |
| Concretely: inserting a key version with attacker-chosen RKM; inventing an OWNER or ADMIN account and signing with it; injecting an envelope or a commitment for one member (a split view) or a new invitee; adding recipients the creator did not choose (AG-03) | A compromised member device, which holds that member's keys (T-23, L-01) |
| | A malicious legitimate OWNER or ADMIN, who can leak keys by design (insider risk, T-37) |
| | Withholding of newer versions or of revocations by the server (T-32, L-10) |

## Decision

### 1. The identity becomes a bundle of two key pairs

| Key | Algorithm | Purpose | Never used for |
|---|---|---|---|
| Encryption key | RSA-OAEP-3072, e = 65537, SHA-256 (CP-02, unchanged) | Receiving 32-byte values: room key material, SEKs, the vault pair-check value (INV-17) | Signing |
| Signing key | ECDSA on P-256 with SHA-256 (CP-26, new) | Signing canonical statements: the identity binding, vault re-wrap requests, and from Phase 6 room statements | Encryption, key wrapping, key agreement |

Both keys are generated together in the browser at vault setup and share one client-generated identity key ID. The two purposes are never mixed (principle 6). Signatures use the IEEE P1363 encoding (r || s, 64 bytes) that WebCrypto produces. The signature nonce is generated by the browser's or Node.js's cryptographic library, never by CipherMesh code.

### 2. Identity binding and fingerprint

- **Binding signature.** The signing key signs the canonical statement `cm.identity.binding` containing the user ID, key ID, suite and both SPKI public keys. The API verifies it at upload, and every client verifies it before it uses another user's public identity. It proves possession of the signing key and binds both public keys to one account and key ID, so a copied public key cannot be attached to another account.
- **Fingerprint (CP-17 revised).** `SHA-256(JCS(cm.identity.fingerprint {suite, encryptionKeySpki, signingKeySpki}))`, shown as 64 hexadecimal characters in 16 groups of four. One out-of-band comparison covers both keys. Each client computes the fingerprint from the keys it actually uses and never displays a fingerprint string received from the server as if it were verified.

### 3. Effect on the vault (Phase 4)

The vault stores both private keys, each wrapped with AES-256-GCM under its own wrapping key derived with HKDF from the Argon2id output (different `purpose` in the info context), so each wrapping key encrypts exactly one message per vault write. The AAD binds the user, the key ID, the purpose, the identity fingerprint and the vault format version. The format is specified in [cryptographic-architecture.md](../../crypto/cryptographic-architecture.md) section 5 and [vault.md](../../crypto/vault.md).

A vault re-wrap (passphrase change or parameter upgrade) is signed with the identity signing key over `cm.vault.rewrap`, which names the previous salt, the new salt, the new parameters, and the new IVs and wrapped private keys themselves. The API verifies the signature against the stored signing key and applies the change only if the previous salt is still current. A stolen session, even together with the account password, therefore cannot silently replace the encrypted private keys of an identity. A vault reset after a lost passphrase cannot be signed by the lost key; it creates a new identity with a new fingerprint and stays visible to the user's contacts (see Key-Lifecycle Implications below and [key-lifecycle.md](../../crypto/key-lifecycle.md) section 3).

### 4. Signed room statements (Phase 6 and Phase 11)

The identity format above is decided now. The room statements are decided in principle now and specified exactly, with tests, in Phase 6 (CM-T033 to CM-T036) and Phase 11 (CM-T050):

1. **Room genesis.** The room creator signs `cm.room.genesis` (room ID, creator user and key ID, suite). It is the root of the room's authority chain.
2. **Membership grants.** Every invitation is signed by its inviter, and every grant of the ADMIN role and every ownership transfer is signed by the OWNER at that time (`cm.room.membership-grant`: room, subject user and key ID, role, grantor user and key ID).
3. **Key-version statements.** The OWNER or ADMIN who creates version v (room creation or rekey finalize) signs `cm.room.key-version`: room ID, version, commitment RKC_v, the previous version's commitment, suite, creator user and key ID, and the sorted list of recipient user and key IDs.
4. **Envelopes are authenticated through the signed commitment.** A recipient decrypts its envelope, recomputes RKC_v from the decrypted RKM_v and requires equality with the signed commitment. No per-envelope signature is needed, because finding different key material with the same commitment would break HKDF-SHA-256 (CD-24).
5. **Verification rule.** A client uses key version v only if the creator's public identity verifies (binding signature and fingerprint), the key-version statement verifies under the creator's signing key, the creator's OWNER or ADMIN authority follows from a chain of signed grants back to the genesis statement, the recomputed commitment matches the signed one, and the client's own identity is in the signed recipient list. Otherwise it refuses the key, shows a security alert and reports `KEY_AUTHENTICATION_FAILED`.

This is digital signatures over canonical, domain-separated statements, the same pattern used by signed group-state changes in established designs (for example MLS proposals and commits signed with credential keys). No new primitive or construction is introduced: the argument rests on the unforgeability of ECDSA and on SHA-256 and HKDF.

### 5. Complements kept

Fingerprint comparison stays the root of trust for identities (T-25): mandatory in RESTRICTED rooms, prompted elsewhere. Fingerprint pinning (OCD-06) remains a recommended stretch goal, and it becomes more valuable now that verified identities anchor the authority chain. The Room Safety Code keeps its role for split views and rollback (ADR-012).

## Alternatives Considered

| Option | Main advantage | Why not chosen |
|---|---|---|
| **B. Authenticator chained to the previous room key** (a MAC over version v+1 keyed from RKM_v) | No new identity key | Stops only attackers who never held a room key. A removed member colluding with the server holds RKM_v, which is exactly the case a rekey must cover. Version 1 and new invitees have nothing to verify against |
| **C. Fingerprints only** (baseline) | No change | Authenticates identities, not who created a key version. T-36 stays open |
| **D. Trust on first use only** (OCD-06) | Detects later key changes of known contacts | Does not authenticate key versions; per-device state. Kept as a complement |
| **E. Key transparency log** | Strong, auditable directory | A large additional system, out of scope (also rejected in ADR-012) |
| **F. Messaging Layer Security (RFC 9420)** | Standardized group key agreement with authenticated membership, forward secrecy and post-compromise security | Replaces the whole room-key design; large protocol and dependency, hard to implement and explain here (rejected in ADR-004) |
| **G. HPKE authenticated mode (RFC 9180)** | Sender-authenticated envelopes | Requires replacing the RSA-OAEP identity with Diffie-Hellman keys and a cryptographic library; authentication is pairwise and not verifiable by third parties, so the key version itself stays unattributed; not resistant to key-compromise impersonation |
| **H1. Signing with the existing RSA key (RSA-PSS)** | One key pair | Uses one key for two primitives, which breaks key separation; WebCrypto also binds each key to one algorithm |
| **H2. A second RSA key pair for RSA-PSS-3072** | Standardized and native | 422-byte public key, 384-byte signatures and a second multi-second key generation on slow devices, for the same 128-bit security level as P-256 |
| **I. Ed25519 signing key** | Deterministic signatures, small keys, already used for audit checkpoints (CP-14) | Playwright's WebKit build, one of the three engines CipherMesh tests, refuses Ed25519 with `NotSupportedError` (probe below). INV-15 would make vault setup fail there. ECDSA P-256 works in every engine. Ed25519 stays a candidate for a future suite |
| **J. WebAuthn (passkey) signatures** | Keys never leave an authenticator; phishing-resistant | Not every user has an authenticator; synchronisation across devices varies; the assertion format is complex. Revisit with OCD-11 |

## Consequences

- The identity, the vault format and the `user_key_pairs` table gain a signing key, its wrapped private key and the binding signature (one reviewed migration in Phase 4). No identity exists yet, so nothing has to be converted.
- Key generation adds an ECDSA key pair, which takes milliseconds; RSA-3072 generation stays the dominant cost.
- The API verifies ECDSA signatures with Node.js WebCrypto (LIB-02). Client and server build the signed statements with the same canonical builders in `packages/crypto`, so both sides sign and verify identical bytes.
- Phase 6 stores the genesis, grant and key-version signatures and implements the verification rule; Phase 11 signs rekey finalize payloads. Their data-model additions are listed in [data-model.md](../data-model.md) section 4.5 and section 8.
- The UI shows who signed a key version and flags any statement that fails verification.
- CD-11 ("no per-user signing keys") is superseded by CD-23. Key versions become cryptographically attributable to their creator; content attribution still relies on the server (L-09).

## Security Implications

| Attack | Before | After Phase 6 implements section 4 |
|---|---|---|
| Server stores a key version with its own key material | Undetected (T-36) | Rejected: no valid signature by an authorized member |
| Server invents an ADMIN account and signs with it | Not applicable | Rejected: no grant signed by the OWNER |
| Server gives one member or a new invitee a different key or commitment (split view) | Detected only by comparing Safety Codes (T-29) | Rejected: the commitment is signed, and the decrypted key must match it |
| Server adds a recipient the creator did not choose (AG-03) | Hidden unless someone reviewed the recipient list | The recipient list is signed by the creator; members can inspect it. A malicious server still cannot obtain RKM without a wrapped copy, and only key holders can wrap |
| Server substitutes a member's whole identity, or the OWNER's for a new invitee | Fingerprints only (T-25) | Unchanged: detected by fingerprint comparison or pinning. Signatures reduce T-36 to this identity-substitution problem |
| Server withholds a newer version or a revocation | Undetected (T-32) | Still undetectable in general. The previous-commitment link exposes forks to clients that hold the earlier version, and Safety Codes expose split views when compared |
| Theft of a member's signing key | Not applicable | The thief can sign as that member until the identity is reset (CM-T053, R5) |
| Malicious JavaScript from a compromised server | Undetected (L-02) | Unchanged |

Residual risk T-36 falls from "unresolved" to "requires identity substitution, a legitimate member's keys or control of served code". The threat model re-rates it only when Phase 6 implements the verification. Tests: the binding signature and fingerprint vectors in Phase 4; in Phase 6 the `key-injection` suite (unsigned, forged, wrongly attributed and unauthorized versions, commitment mismatch, missing recipient) and a negative control that removes the verification.

## Browser Compatibility

Probe of WebCrypto in the Playwright engines used by CipherMesh (2026-10-05; Chromium 153, Firefox 155, WebKit with a Safari 26.6 user agent, on Windows):

| Capability | Chromium | Firefox | WebKit |
|---|---|---|---|
| ECDSA P-256 generate, sign, verify; 91-byte SPKI, 138-byte PKCS#8, 64-byte signatures | Yes | Yes | Yes |
| Ed25519 generate | Yes | Yes | **No** (`NotSupportedError`) |
| RSA-OAEP-3072 generate (300 to 700 ms) and OAEP label, wrong label rejected | Yes | Yes | Yes |
| AES-GCM `wrapKey` and `unwrapKey` of both private keys in PKCS#8, unwrapped as non-extractable | Yes | Yes | Yes |
| PKCS#8 keys exported by each engine import and sign correctly in the other two | Yes | Yes | Yes |

RSA PKCS#8 exports differ by one or two bytes between engines (1793 to 1795 bytes, from DER integer encoding), so length checks use ranges. Missing primitives fail closed (INV-15). The Phase 4 Playwright suite repeats these checks with the real vault code, including a vault created in one engine and unlocked in the other two.

## Key-Lifecycle Implications

- Both key pairs are created, re-wrapped (passphrase change), superseded (vault reset) and revoked (account deletion) together, under one key ID and one status. There is no separate rotation of the signing key in the baseline.
- Public keys of SUPERSEDED and REVOKED identities are kept (data-model section 5), so statements signed before the change stay verifiable. New statements must be signed by an ACTIVE identity; the API refuses others.
- A suspected identity compromise (CM-T053, R5) covers both keys: the identity is replaced and every room of the user enters REKEY_REQUIRED.
- Room administrators see a notice when a member's identity changes, because an unexpected change can indicate substitution (T-25).

## Migration Implications

- No user identity exists before Phase 4, so the migration adds the new columns and constraints without converting data. It fails rather than guesses if a key-pair row exists.
- `user_key_pairs.public_key_fingerprint` keeps its name and now holds the identity fingerprint over both public keys (CP-17).
- A later suite (for example Ed25519 signatures or a post-quantum KEM) gets a new suite identifier and a new vault format version; CM1 records are never reinterpreted.

## Status

Accepted by the project owner on 2026-10-05, before any identity code was written. Sections 1 to 3 are implemented in Phase 4 (CM-T023 to CM-T028) and confirmed by these tests:

- `packages/crypto/src/signing.test.ts`: the 114 Wycheproof ECDSA P-256 SHA-256 P1363 cases and RFC 6979 A.2.5.
- `packages/crypto/src/identity.test.ts`: the binding signature and the fingerprint over both keys (computed independently), and refusal of any modified field, of keys copied to another account and of a substituted encryption key.
- `tests/vault/rewrap.test.ts`: a re-wrap modified after signing, signed by another identity, replayed or stale is refused.
- `tests/e2e/vault.spec.ts`: a vault created in Chromium opens in Firefox and WebKit with the same fingerprint.
- Negative controls NC-04-05 and NC-04-07 in `scripts/security/negative-controls.mjs`.

Section 4 is confirmed or revised by the Phase 6 and Phase 11 tests. Review if a WebCrypto signature algorithm becomes unavailable in a supported engine, if Ed25519 becomes available in every engine CipherMesh tests, or if key transparency or MLS enters the scope.
